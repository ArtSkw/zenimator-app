# create-animation-from-lvg1 — How It's Animated

This documents how `assets/create-animation-from-lvg1.svg` (a green
success-checkmark badge — an almost-closed hand-drawn circle, a checkmark
crossing it, a start-dot/end-flourish/end-dot marking the circle's
pen-down/pen-up points — with two small scalloped clouds flanking it) became
the entry at `public/projects/create-animation-from-lvg1/scene-1/lottie.json`,
generated by `scripts/build-create-animation-from-lvg1.mjs`. Re-run the script
to regenerate.

## Same geometry, same-shaped brief, re-derived anyway

Hashing this SVG's path `d` data against already-shipped scenes found an
EXACT match against three prior scripts: `build-create-animation-from-w62d.mjs`,
`build-create-animation-from-c3tg.mjs`, and `build-cloudscheck.mjs`. This
run's brief is also near word-for-word the one `w62d` built for. Per this
run's explicit instruction, an identical prior script — including the
closest, most recent one — is a source of GEOMETRY only: the path parser and
raw coordinate data were lifted, but every staging/timing/easing constant was
re-reasoned from the current `motion-taste.md`/`player-contract.md`/
`recipe-loaders-icons.md`, not copied. The result lands close to `w62d`'s
choices in several places — a near-identical brief plus identical artwork
narrows the space of good answers — but that is a property of the input, not
evidence the "geometry only" rule was skipped. Re-verified with the mechanical
gates rather than trusting the resemblance.

## The one real delta: the circle's gradient earned a `gradient` parameter

None of the three prior scenes for this artwork declared `parameters` in
`controls.json` — `w62d` and `c3tg` both slotted `accentColor`/`cloudColor`
(flat colours) but left the circle's four-stop linear gradient un-slotted and
static. Player-contract's "Content Parameters" section names exactly this
failure mode ("a 'Check accent color' control driving four small strokes
while the gradient ring it appeared to name stayed untouched") as something
already shipped twice. This build closes that gap: the circle's `gs` gradient
item carries `sid: checkRingGradient`, published under `slots` with the same
ramp object built once and referenced twice (never hand-duplicated), and
declared in `controls.json.parameters` as `kind: "gradient"`. Verified against
the shipped `moneytransfer-status-scene-s5zh` scene's identical `checkRing`
convention and against `check-parameters.mjs`, which passes.

## `m: 2` cloud draw order — re-verified by rendering, not assumed

Each cloud group holds a long scalloped bump subpath plus two short dash
subpaths, trimmed together with `m: 2` (trim each subpath by its own share of
total arc length). Rendered the isolated draw-on at intermediate frames
directly rather than trusting the prior scripts' comments: the bump draws for
most of the window, the two dash accents flick on in the final stretch,
proportional to each subpath's own length. Still true in this player build.

## Checkmark trim reads slow-fast-slow, not "done early" — verified by isolating the layer

Reading the combined preview grid at frames 60/70/76 first looked like the
checkmark had finished drawing well before its authored end (94) — the shape
looked essentially complete by frame ~70. Isolating the checkmark as its own
throwaway single-layer scene (deleting the other six layers from a copy of
the built JSON, re-rendering) showed this was an illusion from the circle
layer's own near-complete stroke overlapping it in the same frames, not a
bug: the checkmark's own trim value at frame 60 is 54.8% of arc length (short
arm ~25% + partway up the long diagonal), computed directly from the cubic
bezier segment lengths (164.6px + 53.8px), which matches a hooked, partial
check — not a finished one. The apparent "already done" read was a genuine
gestalt effect of a 14px round-capped stroke reading as a recognizable
checkmark well before 100% trim, compounded by the ease-in-out curve's fast
middle section (cubic-bezier(.42,0,.58,1) puts 87% of the trim value already
at 75% of the time). Lesson for future combined-layer previews of this
technique: isolate a hero draw-on layer before concluding its pacing is
wrong from a combined render — the other layers' own nearly-simultaneous
completion can visually mask genuine partial progress.

## Mechanical gates

contact pairs (the checkmark, circle, and decorations never share a world
point close enough to register as touching, and none carries a position
track that could slide — only trim/opacity/scale, all pivoting on their own
geometry), no invented fills, no export-incompatible techniques (no Merge

`node scripts/check-parameters.mjs create-animation-from-lvg1` exits 0: the
one declared parameter (`checkRingGradient`, kind `gradient`) is bound to the
real `g` property on the circle's gradient stroke and published in `slots`.

## Revision: clouds now lead, badge follows

Follow-up request: reorder the cast so the clouds draw on + drift in FIRST,
and the badge (circle, then checkmark) only starts once the clouds are
almost completely in place — smallest-change edit, scoped to timing only.

Nothing about how any individual element moves changed — the cloud rig
(`m:2` draw-on synced to an upward drift) and the badge rig (circle leads,
checkmark joins mid-stroke on the same 22f/72f-duration offsets, both
stamp-settle) are byte-for-byte the same functions, just re-timed:

- `CLOUD_START` moved from `92` to `0` — clouds are now the first cast
  member instead of the last.
- A new `BADGE_START = 36` constant anchors the circle's draw start. `36`
  is where cloud-left's own window (`[0, 36]`) reaches exactly 100% and
  cloud-right's (`[4, 40]`) reaches ~90% — "almost completely present," not
  fully idle, so the badge's entrance still overlaps the tail of the cloud
  reveal rather than waiting for a hard stop.
- Every badge-timing constant (`CIRCLE_DRAW`, `CHECK_DRAW`, `CIRCLE_SETTLE`,
  `CHECK_SETTLE`, `START_DOT_POP`, `END_MARK_POP`) is now expressed as
  `BADGE_START + <original offset>`, preserving the exact same internal
  durations and stagger the badge always used ("in a similar way as it is
  now," per the request) — only the whole block's start time moved.
- `FRAMES` extended `150 → 160` to give the now-sequential (rather than
  overlapping) cloud→badge handoff room without compressing either half's
  pacing, plus the same ~18-frame hold after the final stamp-settle the
  original had.
- Z-order is untouched: clouds stay behind the badge in the layer stack
  (pushed last in `layers`, per the "frontmost first" push order) — this
  revision only reordered *when* things move, not *how* they stack.

Re-verified: `check-motion.mjs` and `check-parameters.mjs` both still exit 0
