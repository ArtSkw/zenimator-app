# create-animation-from-w62d — How It's Animated

This documents how `assets/create-animation-from-w62d.svg` (a green success
checkmark inside a hand-drawn circle, with two small scalloped clouds) became
the entry at `public/projects/create-animation-from-w62d/scene-1/lottie.json`,
generated by `scripts/build-create-animation-from-w62d.mjs`. Re-run the script
to regenerate.

## Same geometry, re-derived rig — the "prior script is geometry only" rule in practice

Diffing this SVG's path `d` data against already-shipped scenes found an exact
match: `scripts/build-cloudscheck.mjs` and `scripts/build-create-animation-from-c3tg.mjs`
ship the identical circle/checkmark/cloud geometry. Per this run's explicit
instruction, that match licenses reusing the GEOMETRY only — not the staging,
timing, or easing choices. Re-parsed the same path data fresh and re-derived
every motion decision against the current `motion-taste.md`/`design-taste.md`/
`player-contract.md`, landing on one deliberate difference from both priors:

**Read "the checkmark draws itself... WITH the circle also drawing" as
concurrent, not sequential.** Both earlier scenes staged circle-then-checkmark
(fully sequential). This brief's grammar ("X does A, with Y also doing B")
reads as simultaneous action, so this build has the circle lead by a short
head start (it's the larger "frame" the checkmark reads against) and the
checkmark start while the circle is still mid-stroke — both drawing over
most of the same window, finishing close together. This is the kind of
per-brief re-read the "geometry only, not rig topology" instruction exists to
force: an identical source asset does not imply an identical animation is
correct for a differently-worded brief.

## `m: 2` cloud draw order — verified by rendering, not assumed from the prior comment

The earlier scripts' comments claim `m:2` (trim each subpath individually)
draws the long scalloped bump for most of the window, then flicks the two
short dash accents on right at the end, proportional to each subpath's own
arc length. Rather than trust that comment, this run re-verified it by
rendering intermediate frames of the cloud draw-on directly (`f105`, `f115`,
`f120`, `f123` at high zoom): the bump visibly grows first, the two dashes
flick on in the final ~15% of the window. Confirmed still true against this
scene's own group order (`bump, dashL, dashR` in the `it` array, trim last).
Worth re-checking on any future scene reusing this technique rather than
citing the prior comment — the point of "re-derive, don't inherit" is exactly
that a claim like this could silently stop being true after a player update.

## Hierarchy-scaled completed-gesture stamps

Every drawn stroke gets a stamp-settle (motion-taste's "a completed gesture
gets punctuation"), sized by role: the checkmark (the brief's own hero — "the
visible checkmark" opens the sentence) gets the strongest pop (+4% scale
overshoot); the circle (the supporting frame) gets a quieter one (+2%); the
decorative pen-down/pen-up marks (start-dot, end-dot, end-flourish) get a
slightly livelier +6% since they're small enough to read as playful accents
without competing with the hero. All three share the same easing anchor
(this scene's global consistent ease-in-out) — only the overshoot magnitude
carries the hierarchy, per motion-taste's "only the focal element gets the
strongest personality."
