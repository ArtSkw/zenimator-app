# Live Onboarding Companion (Double-Bicep Flex) — How It's Animated

This documents how `assets/live-onboarding-companion-i8ek.svg` (zenek mid
double-bicep flex, "Making great progress" speech bubble) became the
`intro-loop` scene at
`public/projects/live-onboarding-companion-i8ek/scene-1/lottie.json`,
generated by `scripts/build-live-onboarding-companion-i8ek.mjs`.

Unlike the deck-chair siblings (`eh0n`/`ler6`/`ire9`/…), this source SVG is a
genuinely different rig pose — same "zenek" character family (round dark
body, white face, two closed happy-arc eyes) but arms already flexed into a
double-bicep pose, and a first for this family: the ground shadow is filled
with an embedded raster `<pattern>` (a tiled base64 PNG), not a flat tint.

`viewBox="0 0 240 240"`. All geometry is read LIVE from the SVG at build
time via a small `tagById()`/`pathD()`/`attr()` extractor (never hand-
transcribed) — the long path strings are too easy to mistype by hand, and a
build script that re-derives from source is the whole point of "the build
script is the durable artifact."

- Tooltip plate: `x=14 y=14 w=189 h=35 rx=17.5` — wider than the other
  siblings' 176 (sized for "Making great progress"), but the same H, so the
  same vertical stage-shift/headroom math (`SHIFT_Y=4`, `PLATE_CENTER_Y=44.5`)
  applies unchanged.
- Trail circles: `Ellipse 2420`/`2421` at the exact same cx/cy/r as every
  sibling — reused the established re-centered placement (120/79 large,
  132/92.5 small) rather than re-deriving.
- Character: `Group 1000007766` > `body` (shadow), `Vector` (bg blob, white),
  `Union`/`Union_2` (white arm cutouts), `Group 1000007121`/`1000007122`

## Part-role identification is not always what the id numbering suggests

Read the actual parsed bboxes before assigning roles — id order and "circle
vs path" are not reliable proxies for anatomy. In `Group 1000007121` (right
arm), the SMALLEST-y (topmost, nearest the head) shape is `Ellipse 489`, a
general 4-vertex path — and topmost-in-a-raised-bicep-pose is exactly where
the FIST sits (hand curled near the head). The circle, `Ellipse 487`, sits at
a LOWER y (mid-height) — a knuckle/bicep bulge, not the fist. A first pass
assumed "the circle is obviously the fist" (a reasonable prior — a clenched
fist reads as round) and wired the "fists tighten fractionally at the peak"
accent onto the wrong shape; the render still looked plausible (something
pulsed) but the pulse landed on the least visually prominent part of the arm
(the circle is painted UNDER `Ellipse 489`, so `489`'s later doc-order paint
mostly occluded it) rather than the terminal cap the eye actually reads as
"the fist." Fixed by computing each candidate shape's bbox first and picking
the true topmost/terminal one before wiring the accent.

## Raster pattern shadow — the fallback path, and its two bugs

The shadow (`body`, `fill="url(#pattern0_5390_69337)"`) tiles a 128×128
base64 PNG via `patternContentUnits="objectBoundingBox"`, tile size
`0.370936 × 1.70293` of the shadow ellipse's own bbox (≈22×22px absolute —
computed from the pattern's own authored fractions, not guessed). Too
photographic/intricate to revectorize faithfully as a hatch, and it only
ever moves as one piece (a uniform widen/narrow scale, never rotates) — so
this used svg-compatibility.md's documented fallback: decode the embedded
PNG to a real image asset at build time, tile `Math.ceil(bboxW/tileW)`
image layers (3, here) across the ellipse, and clip each with a per-layer
mask (simpler than a track matte — no array-adjacency bookkeeping needed for
3 independent tiles).

Two bugs found and fixed, both now promoted into svg-compatibility.md:

1. **Mask coordinate space.** A layer mask's `pt` path lives in that layer's
   own LOCAL, pre-`ks` space — i.e. the image's native 128×128 px box, not
   the post-transform stage space the tile ends up occupying on screen.
   First pass only translated the clip shape into the tile's local origin
   (`v - tileOffset`) and left it there; the mask ended up sized in ~22px
   stage units inside a 128px-native local space — about 5.8× too small —
   so only a thin sliver of each tile showed (rendered as scattered
   diagonal dashes instead of a filled ellipse band). Fixed by ALSO applying
   the inverse of the layer's own `ks.s` (native/tile ratio) to every mask
   vertex and `i`/`o` handle delta, not just translating.
2. **Rest-value offset via `1 - driver`.** See the promoted motion-taste.md
   "world responds" addendum — the shadow-widen and chest-puff tracks were
   both originally written as `amplitude * (1 - squeeze(t))`, which is
   `amplitude`, not 0, when `squeeze(t)==0` at true rest — silently
   offsetting frame 0 (and every inter-cycle flat gap) away from the
   unmodified source silhouette. Fixed by flipping to `amplitude *
   squeeze(t)` (or its negation) so rest is always exactly 0 offset,
   verified by confirming `squeezeEnvelope(0) === 0` drives every dependent
   track to its literal baseline value.

## The pump — one shared envelope drives the whole cast

`squeezeEnvelope(t) = waypointCurve(t % IDLE, waypoints)` — a single
smootherstep waypoint chain (anticipation dip, slow build to peak, brief
hold, softer release, flat rest) that every dependent track reads: arm
position/rotation (mirrored, Lissajous-phase-offset X/Y for a genuine arc
per motion-taste.md Fluidity), fist own-center scale, eye handle-scale
(deepens the closed-arc curve — same vertex count, only `i`/`o` handle
magnitude changes), chest/face silhouette squash (counter-phase), and
shadow width (counter-phase). Being a pure function of `t % IDLE` means
every track is alive from frame 0 with zero echo/tileForward bookkeeping,
and the seam is exact by construction whenever `op = T + n·IDLE` (proved,
not just hoped, by the pixel diff below).

A brief 1.4px isometric quiver (windowed high-frequency wobble, active only
during the squeeze's hold plateau) rides on top of the arm position as the
loop's one snappy accent — "the isometric-hold tremble, 1-2px, that's the
joke."

## Motion craft pass — the arms actually flex, the tremble reads (2026-08-06)

Team feedback measured two defects: (1) 12 of the 30 arm-related layers had
NO track of their own — only `arm-*-rig` (position/rotation) and the fist's
own scale animated, so the arms rose/fell/spread as two rigid boards, never
changing shape; (2) the isometric-hold tremble's half-cycle was 2 frames
(~15Hz), reading as a buzz, not a felt strain. Both are now the case study
behind motion-taste.md's "Articulate the PARTS" and "Accents must be
readable" rules — this scene is literally the "flexing-mascot scene" example
quoted there.

**New rig, per arm** (`buildArm`, `scripts/build-live-onboarding-companion-i8ek.mjs`):

- `arm-{side}-elbow` (new `ty:3` null, child of `arm-{side}-rig`): anchor and
  position both at the knuckle circle's center — the exact geometric seam
  between the shoulder mass (486, proximal) and the forearm mass (488,
  distal), a real hinge read from the parsed bboxes, not guessed. Its
  rotation is `mirror * ELBOW_FLEX_DEG(14) * squeezeEnvelope(t)`: the elbow
  closes on the squeeze, opens on release. The forearm (`arm-*-bicep`
  layer — yes, the LAYER named "bicep" holds the geometrically-forearm
  path per the file's existing part-ID convention, see "Part-role
  identification" above), the knuckle, and its hilite (`hilite-a`) are now
  parented to this null instead of the rig directly, so they fold as one
  distal unit.
- `arm-{side}-blob` (the shoulder/upper-arm mass, 486) changed from a static
  shape layer to an **animated shape layer**: `squashSubpath` (the same
  area-conserving squash already used for the chest) contracts it 8% along
  its own long axis (shoulder-center → elbow, derived not guessed) at peak
  squeeze, which widens it ~8.7% perpendicular — the double-bicep bulge,
  peaking in sync with the elbow closing.
- `arm-{side}-wrist` (new `ty:3` null, child of `arm-{side}-elbow`): carries
  only the fist and `hilite-b`. Its rotation is the SAME squeeze function
  sampled at `t - FIST_LAG_FRAMES(5)` (the ARC_LEAD idiom already used for
  the rig's own X/Y phase offset — a continuous re-sample, never a
  time-shifted copy of keyframes), giving the fist's curl a beat of delay
  after the elbow. The fist's own scale pulse (`FIST_GAIN_PCT`) got the same
  lag for a consistent "settles after" read.
  - **Pivot gotcha caught before shipping**: the first version anchored the
    wrist null at the FIST'S OWN bbox center (matching the existing
    "own-center pulse" idiom used elsewhere in this file). That is wrong for
    a LAG null specifically — since the fist layer's own local point already
    coincides with that anchor, `R(rotation)·(point − anchor) = R(rotation)·
    (0,0) = (0,0)` for any rotation, so the wrist's rotation contributed
    ZERO positional offset, only a self-spin of the fist shape in place. Fixed
    by pivoting the wrist at the SAME point as the elbow (the shared joint),
    so the delayed rotation swings the fist through a real arc. Promoted to
    motion-taste.md's "Extremities lead or lag their root" bullet since this
    is a general trap for any nested lag-null, not specific to this scene.
- Tremble retimed: `QUIVER_LO/HI` widened from `[60,78]` (18f) to `[54,84]`
  (30f, still centered on the squeeze's hold plateau) and cycle count dropped
  from 4 to 3 — half-cycle = `30/(2*3) = 5` frames (6Hz @ 60fps), inside the
  "readable, felt" 5–6f band, total window 0.5s (≥ the 0.4s/24f floor).
  `QUIVER_AMOUNT` (1.4px) is unchanged — frequency alone was the defect, per
  the rule: "amplitude does not rescue frequency."

## Phase-timing fix — the tremble (and its siblings) fired at the wrong beat (2026-08-07)

Team feedback, verbatim: "the tremble happens when the arms straighten
instead of bending to show off its flexed biceps." The prior pass's own
verification (b) had measured `arm-elbow` rotating "0°→14°" and fist-to-
bicep-center distance shrinking 40.15px→35.58px at local t=66, and called
that peak contraction — but that reading trusted the rotation magnitude and
a plausible-sounding distance metric without checking which pose either one
actually renders as. It was wrong.

**The real geometry, measured three ways:**

1. **Direct render.** `arm-left-elbow` is −14.0° at frame 60 and +1.4° at
   frame 164 (both are `local t=60` and `local t=20` of the same
   `squeezeEnvelope`). Rendering both frames zoomed shows −14° is the arms
   OPEN/EXTENDED pose (fists high, more separation from the bicep mass, the
   `hilite-b` highlight peeking out from behind the fist) and +1.4° is the
   tighter, more tucked pose — the reverse of what the rotation's own sign
   suggests.
2. **Fist-to-head world distance** (full nested transform chain, rig→elbow→
   wrist→fist, replayed by hand and cross-checked against the rendered
   pixels): minimized at local t≈23 (80.79px), maximized at local t≈65
   (90.06px). "Closest to the head" — the brief's own literal phrase — is
   unambiguous: peak contraction is the anticipation dip (`squeezeEnvelope`'s
   own numeric MINIMUM, v=−0.10 at t=20), and the `[60,78]` "hold" plateau
   (`squeezeEnvelope`'s own numeric MAXIMUM, v=1.0) is the extended pose.
3. **A rotation-invariant sanity check that turned out to be the wrong
   question**: the intrinsic elbow FOLD ANGLE (bicep axis vs. forearm axis)
   DOES minimize at the `[60,78]` hold (45° vs. 65° at rest) — the joint
   really does bend tightest there. This is why the prior pass's number
   looked plausible: the elbow genuinely folds more. But the whole arm ALSO
   rises and swings outward as it folds (the rig's own position/rotation,
   unchanged in this pass, compounds in the same rotational sense as the
   elbow), so the net effect on fist-to-head distance is the opposite of
   what the fold angle alone suggests. Promoted to motion-taste.md: a
   geometrically rigorous metric can still answer the wrong question if it
   isn't the one the brief's literal wording specifies.

The prior pass's own "40.15px→35.58px" figure could not be reproduced —
recomputing the identical fist-to-shoulder(486)-center metric (rest value
matches exactly, 40.15px, confirming same reference points) gives
43.20px at local t=65-66, an INCREASE, not the claimed decrease. Left here
as a correction to the record: that number was itself very likely another
instance of the same sign-convention trap, not a second, independent bug.

**Fix.** The primary rig (arm-rig position/rotation, arm-elbow flex,
arm-wrist lag, arm-blob bicep bulge) is contractually frozen and reads
`squeezeEnvelope` directly, unchanged. Everything secondary that was ALSO
reading `squeezeEnvelope` directly — and therefore inherited its wrong-beat
peak — now reads a new derived `contractionEnvelope(t)`: 0 across the whole
build/hold/release arc (including the visually-extended `[60,78]` plateau),
ramping to 1 exactly at local t=20 (`squeezeEnvelope`'s own dip,
`Math.min(1, -squeezeEnvelope(t)/0.10)`), and back to 0 by the time squeeze
crosses back through zero (~t=30):
- `QUIVER_LO/QUIVER_HI` retimed from `[54,84]` (centered on the false-peak
  hold) to `[5,35]` (centered on t=20, the true peak) — same 30-frame width,
  same 3-cycle/5-frame-half-cycle oscillation shape, untouched.
- fist scale bump (`FIST_GAIN_PCT`), eye handle-scale (`EYE_HANDLE_GAIN`),
  chest/face squash (`CHEST_PUFF_PCT`), and shadow scale
  (`SHADOW_WIDEN_X/Y_PCT`) all switched from `squeezeEnvelope(t)` to
  `contractionEnvelope(t)` (fist keeps its existing `FIST_LAG_FRAMES` delay
  on top). Bicep-blob bulge was NOT touched — it's contractually frozen —
  so it still peaks with the rig's own `[60,78]` hold; this is a known,
  accepted mismatch, not something this pass could fix without touching
  frozen articulation.

**Verification:**

## Living-idles pass — trail float, body breathe, dead-track audit (2026-08-07)

Team feedback: the idle segment (`54..198`) had two "the world stopped"
defects even though the arm rig itself was fully alive. Both are the exact
case studies motion-taste.md's "Living idles" section had just been extended
with:

- `trail-large`/`trail-small` (the thought-trail circles) had a one-shot
  pop-in on `s`/`o` and NO position track at all — once the pop settled
  (~frame 22, well before `T=54`) they were pixel-static stickers for the
  entire loop.
- `zenek-body`/`zenek-face` DID move — 73 morph keyframes each, driven by
  `contractionEnvelope` (the "chest recedes at true peak contraction" read)
  — but `contractionEnvelope` is only nonzero for a ~16-frame dip once per
  144-frame cycle (`squeezeEnvelope`'s own anticipation dip, `local
  t≈14..30`). Measuring the actual baked keyframes (vertex position AND
  handle tips, per the "handle-only morphs read zero on a vertex-only
  measure" trap) gives **2.408px** max vertex travel on `zenek-body`,
  **2.222px** on `zenek-face` — not the literal 0.00px this task's own brief
  quoted (that number may be from an earlier build or a coarser sample that
  missed the narrow window), but functionally the same defect: for ~89% of
  the loop the body sat completely flat, which reads exactly like the
  "head-and-limbs puppet bolted to a board" the rule warns about.

**Fix 1 — trail float.** Added a position track to `trailCircle()`
(`scripts/build-live-onboarding-companion-i8ek.mjs`), own clock per circle:

- `trail-large`: `CLOCK_TRAIL_LARGE = 72` (2 cycles/loop), amplitude 1.1px,
  sign `+1`.
- `trail-small`: `CLOCK_TRAIL_SMALL = 48` (3 cycles/loop), amplitude 0.9px,
  sign `-1`.

Both periods are divisors of `IDLE=144` (`OP - T`), so `value(T) ===
value(OP)` holds automatically — no boundary special-casing needed, the same
trick `squeezeEnvelope` already relies on. The float is a plain continuous
`sin`, not a `waypointCurve`/smootherstep hold: a drifting dot should never
sit at zero velocity. `floatOffset(t) = sign * amp * sin(2π·((t-T) mod
period)/period)` is defined relative to `T` (not absolute `t`) specifically
so `floatOffset(T) === 0` by construction — that makes the flat 0..T pop-in
hold and the loop's own float meet with no positional pop at the intro/loop
handoff. Measured (dense-sampled every 2 frames, matching the file's own
baking convention): `trail-large.p` range **2.200px** (Y-only, X range
0.000), `trail-small.p` range **1.800px** — both inside the requested
1.5–2.5px band. Phase divergence, read directly off the formula: at `t=60`
(`T+6`), large = `+1.1·sin(30°) = +0.55`, small = `-0.9·sin(45°) ≈ -0.64` —
opposite sign, different magnitude, from a shared start of 0 at `T`. Velocity
audit (1-frame finite differences of the raw formula over the full loop):
`trail-large.p` max/median = **1.36x**, `trail-small.p` = **1.33x** — smooth,
nowhere near the 3x continuous-motion bar.

**Fix 2 — body breathe.** Added `breatheScaleAt(t) = 1 + BREATHE_PCT *

## Eye-squeeze "dead track" re-investigation — false alarm, exact case study of the file's own documented trap (2026-08-07)

squeeze truly couldn't be authored).

**Re-investigation found no defect.** `eyeShapeAt()` (build script, ~line
820) scales each vertex's `i`/`o` handle deltas by `1 + EYE_HANDLE_GAIN *
contractionEnvelope(t)` while leaving `v` (the raw vertex positions)

changes" technique already used and already measured non-zero in the prior
"Living-idles" pass's own dead-track table (`eye-right-path` 1.493px,
`eye-left-path` 1.921px). Because `v` never changes, a measurement that
diffs only the `v` array reads a literal 0.00px — this is exactly the
"handle-only morph reads zero on a vertex-only measure" trap this doc had
already flagged three times over (motion craft pass, dead-track audit, the
skill promotion note). The reported "0.00px" is almost certainly that trap
recurring, not a regression: re-deriving the numbers from scratch (below)

## Entrance-timing fix — the bubble was scaled down to fit a short window, T grown to fit the entrance instead (2026-08-07)

- `144 / 72 = 2` (trail-large float — exact)
- `144 / 48 = 3` (trail-small float — exact)
